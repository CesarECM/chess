# Magic Planning Session #1

**Fecha:** 2026-07-23
**Objetivo:** Backlog maestro del MVP de Chess Puzzle App
**Estado:** Aprobado

---

## Arquitectura aprobada

```
React Native + Expo (iOS + Android + PWA — una sola base de código)
Backend:    Supabase (PostgreSQL + Auth + Realtime)
Tablero:    react-native-chessboard + chess.js
Puzzles:    Lichess open database (500 precargados en Supabase)
FSRS:       TypeScript (fsrs-rs o implementación propia)
Pagos:      AdMob (ads) + App Store Connect + Google Play Billing + Stripe (web)
Analytics:  PostHog
Admin:      PostHog dashboards + Supabase Studio (sin panel propio en MVP)
CI/CD:      EAS Build + GitHub Actions
Legal:      Iubenda o Termly + GDPR
```

---

## Decisiones técnicas

| Decisión | Opción elegida | Razón |
|----------|---------------|-------|
| Tablero de ajedrez | `react-native-chessboard` + `chess.js` | Compatible con Expo, drag&drop y tap-tap incluidos, piezas Staunton configurables. Diferenciador del producto es feed+FSRS, no el tablero. |
| Panel de admin | PostHog + Supabase Studio | Evita sprint completo de desarrollo sin diferenciación. Suficiente para MVP. |
| Orden ELO vs FSRS | ELO primero (S3), FSRS después (S4) | ELO es prerequisito lógico del feed. FSRS depende del loop de puzzle activo. |
| Validación de movimientos | Soluciones precargadas (Lichess) | Stockfish WASM para generación es post-MVP. Validación exacta contra DB es más rápida y predecible. |
| i18n | expo-localization + i18next | Ecosistema estándar, bien soportado en Expo. |

---

## Riesgos

| Riesgo | Probabilidad | Impacto | Mitigación |
|--------|-------------|---------|------------|
| `react-native-chessboard` con bugs en Expo | Media | Alto | Validar en Sprint 2.2 antes de construir encima. Plan B: implementación custom con SVG. |
| FSRS complejo de calibrar correctamente | Media | Alto | Usar librería `ts-fsrs` open source validada contra paper. Agregar tests unitarios en Sprint 4.1. |
| Review lento de App Store | Alta | Medio | Iniciar proceso de revisión desde Sprint 13. Tener builds listos con margen de 2 semanas. |
| Supabase RLS policies con bugs en producción | Media | Alto | Sprint 15.4 dedicado exclusivamente a revisión de seguridad de DB. |
| AdMob rechazo por contenido de ajedrez | Baja | Medio | Categoría "Juegos/Educación" es safe. Pre-validar antes de Sprint 9.1. |

### Sprint 4 — FSRS y Repetición Espaciada
*El diferenciador de aprendizaje.*

- [x] **S4.1** — Implementación FSRS en TypeScript (`ts-fsrs`) — variables S, D, R por puzzle/usuario. **Completado 2026-07-24.** `ts-fsrs@5.4.1` instalado; `src/services/fsrs.ts`: API pública `createProgress`, `reviewProgress`, `getRetrievability`, `isDue`; scheduler con `learning_steps:[]` y `relearning_steps:[]` (puzzles van directo a Review). `UserPuzzleProgress` extendido con `state`, `lapses`, `learningSteps`. `jest` + `ts-jest` configurados; `src/__tests__/fsrs.test.ts`: 13 tests pasan (intervalos, estabilidad, recuperabilidad, vencimiento).
- [x] **S4.2** — Mapeo implícito de calificación — comportamiento del usuario → Again/Hard/Good automático. **Completado 2026-07-24.** `deriveFsrsRating(solved, elapsedMs)` en `services/fsrs.ts`: failed→Again(1), <15s→Easy(4), <60s→Good(3), ≥60s→Hard(2). Timer en `usePuzzleSolver` inicia tras la animación del oponente. `lastFsrsRating` en `usePuzzleStore` para consumo en S4.3. 4 tests nuevos (17 total).
- [x] **S4.3** — Persistencia FSRS en Supabase — tabla `user_puzzle_progress` con estado completo. **Completado 2026-07-24.** `scripts/migrate-fsrs.sql`: DDL tabla + índice. `src/services/identity.ts`: guest UUID generado en primer uso, persistido en AsyncStorage, en memoria tras la primera lectura. `src/services/puzzleProgress.ts`: `loadProgress`, `saveProgress` (upsert), `loadDueProgress`. `usePuzzleSolver`: carga FSRS al cambiar puzzle, guarda fire-and-forget tras resultado. `recordResult()` consolida ELO + calibración + FSRS en un solo punto de llamada. **Acción manual requerida:** ejecutar `scripts/migrate-fsrs.sql` en Supabase SQL Editor.
- [x] **S4.4** — Cola de repasos — lógica para determinar qué puzzles aparecen hoy según FSRS. **Completado 2026-07-24.** `src/services/reviewQueue.ts`: `fetchNextPuzzle` (repaso vencido → nuevo ELO-matched), `buildReviewQueue` (batch para S5 feed, N repasos + N nuevos). `puzzle/[id].tsx`: `handleNextPuzzle` usa `fetchNextPuzzle` en lugar de `fetchRandomPuzzle`. ELO_WINDOW ±200 con fallback sin filtro ELO si no hay puzzles no vistos en rango.

### Sprint 5 — Feed Vertical Infinito
*La experiencia TikTok.*

- [x] **S5.1** — Componente de feed — FlashList vertical con paginación y precarga. **Completado 2026-07-24.** `@shopify/flash-list@1.7.3` instalado. `src/hooks/usePuzzleSolverLocal.ts`: solver con estado local (refs) para feed cards independientes. `src/components/feed/PuzzleCard.tsx`: puzzle full-screen autocontenido. `app/(tabs)/index.tsx`: FlashList con `pagingEnabled`, precarga proactiva a ≤3 puzzles del final (`buildReviewQueue`×10), `onViewableItemsChanged` para activeIndex. Criterio de fluidez en dispositivo físico pendiente de EAS build.
- [x] **S5.2** — Algoritmo de selección del feed — ELO + FSRS + score de viralidad. **Completado 2026-07-24.** `reviewQueue.ts`: `scoreCandidate` (0.5×ELO_match + 0.3×popularity_score + 0.2×reliability_score), `applyTopicDiversity` (max 2 por tema primario con overflow fallback). `buildReviewQueue` acepta `excludeIds` (session history), fetcha pool 3× para scoring/diversidad, ordena por score desc antes de diversificar. `index.tsx`: pasa `sessionHistory` en cada llamada a `buildReviewQueue`.
- [x] **S5.3** — Navegación gestual — swipe up (siguiente), swipe down (anterior en sesión), avance automático tras resolver. **Completado 2026-07-24.** `PuzzleCard`: prop `onStatusChange?(status)` notifica al feed cuando cambia el status del card activo. `index.tsx`: `scrollEnabled={activeStatus !== 'playing'}` — tablero tiene prioridad absoluta mientras el usuario juega; `onActiveStatusChange` dispara auto-scroll 1.5s tras `complete`; timer cancelado si el usuario ya swipeó manualmente (efecto en `activeIndex`); cleanup en unmount.
- [x] **S5.4** — Score de viralidad — cálculo por puzzle (tasa de fallo, retención de sesión, velocidad) y persistencia. **Completado 2026-07-24.** `scripts/migrate-virality.sql`: tabla `puzzle_virality` + función PG `increment_virality` (atomic upsert via RPC). `src/services/virality.ts`: `computeViralityScore` (0.40×fail_score + 0.30×speed_score + 0.30×completion_rate), `recordViralityEvent` (fire-and-forget RPC), `fetchViralityScores` (batch query). `usePuzzleSolverLocal.recordResult`: llama `recordViralityEvent`. `reviewQueue.scoreCandidate`: nuevo param `virality?` (0.25 de peso), fallback 0.5 para puzzles sin datos. `buildReviewQueue`: fetcha viralidad de candidatos en batch antes de scoring. **Acción manual:** ejecutar `migrate-virality.sql` en Supabase SQL Editor.
